# Contradiction Heuristics

Apply these when checking new requirements or in-progress decisions against `arch/ADR.md` and `arch/domain-model.md`, whether in a pre-interview pass or a final backstop scan:

- **Established frameworks, not just data facts.** "Current state" is not limited to data-model facts. Before proposing mechanism options for a functional category (approval process, integration pattern, CPQ configuration, etc.), check `arch/ADR.md` for whether a prior story already established a framework for that category, and default to consistency with it instead of presenting a generic binary choice. Once an established framework is confirmed, also check its adjacent or lifecycle capabilities (e.g., an approval framework's own action-flow hooks) before falling back to a bespoke mechanism (e.g., a status-change Apex trigger) for a related need — the two can overlap and picking the wrong one creates unnecessary complexity or conflicts.
- **Restrictive vs. permissive language.** When a prior design used restrictive language ("locked," "disabled," "cannot," "prevented") for a specific behavior, and new requirements use permissive language ("should be able to," "allow," "can") for that same behavior, treat it as a contradiction candidate even when the wording isn't an exact match.
- **Explicit deferrals.** When a prior design explicitly deferred a capability to a named future story, and the new story's requirements don't mention that deferral, surface it as an early scoping question — "is this still deferred, or now in scope?" — before designing the narrower path in detail. Asked early, this shapes every subsequent decision; asked late, it forces rework.
